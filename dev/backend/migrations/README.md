# Alembic migrations

Alembic owns the Postgres schema. Applied revisions are historical and must not be rewritten.

| Revision | Purpose |
| --- | --- |
| `20260829_0001_itinerary_foundation.py` | Creates `itineraries`, `stops`, `media_assets`, and `generation_runs` with durable lifecycle, lease/fencing, idempotency, evidence, and media metadata. |
| `20260829_0002_natural_request_and_place_links.py` | Renames the request field for 1,000-character natural language, replaces normalized city with resolved destination, adds planned date/timezone, typed place links, generation checkpoint JSON, and a unique itinerary-level hero index. |
| `20260829_0003_city_and_tags_input.py` | Replaces the natural request field with required, separately stored city text and a JSONB preference-tag array. |
| `20260829_0004_preference_learning.py` | Adds the pre-generation learning stage plus sessions, single/pair pages, immutable issued items, and like/dislike responses. |

The current table responsibilities are:

- `itineraries` — city/tags, resolved destination/date/timezone, public-result data, idempotency hash, internal lifecycle, and safe terminal error.
- `preference_learning_sessions` — collecting/completed gate and algorithm version per itinerary.
- `preference_pages` / `preference_items` — ordered journal openings and exact activity JSON shown to the user.
- `preference_responses` — itinerary/item-scoped `like|dislike` records.
- `stops` — ordered local-time places, location/evidence fields, and application-owned `map`, `official`, or `source` links.
- `media_assets` — the required hero image plus provider, app-storage, dimensions, alt text, and diagnostics.
- `generation_runs` — durable attempts, scheduling, leases/fencing, plan checkpoint, fal request checkpoint, and provider diagnostics.

Models are imported by `migrations/env.py`. Review autogenerated revisions and both upgrade/downgrade behavior before applying them.

The runner reads the same `DATABASE_URL` as FastAPI. API and worker never create or upgrade tables. Compose runs the one-shot `migrate` service before API/worker startup; host development uses `make migrate`.
